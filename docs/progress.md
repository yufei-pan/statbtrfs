## Questions waiting for the user
- Decided 2026-11-26, the user's answer (relayed by chief): Q1 (0.46) "Known limitation, release (Recommended)" (the option: as built, no hang on a terminal; those setups fail at once, with a README line and the workarounds, NOPASSWD for btrfs or sudo's noninteractive_auth). Written in docs/limitations.md ("On a terminal, a sudo that signs in with no question is refused when it remembers nothing") and README.txt, released in 0.46. The question as asked: **Q1 (0.46): a sudo that signs in with no question, on a terminal, with nothing remembered: a known limitation?** What the operator sees: statbtrfs run as a user (not root) through the per-command sudo fallback, where sudo authenticates with no question and no NOPASSWD rule (an ssh agent through pam_ssh_agent_auth, Kerberos) and remembers nothing at that moment, is refused, because `sudo -n` does not try. That happens with sudo set to ask every time (`timestamp_timeout=0`); with `-s` or `-w` and `-i` longer than sudo's timeout (5 minutes by default), from the first poll after the remembered sign-in ran out, and a Ctrl-C cancel then says "Could not cancel the scrub on <mount>: sudo: a password is required."; and in a background job whose input is not the terminal (`nohup statbtrfs -s &`, `statbtrfs </dev/null &` from an interactive shell), from the first command, also for a user whose sudo may run everything. The operator sees "Could not fetch complete info for <mount>. Skipping...", exit 2, where 0.45 worked. Runs with no terminal (cron, ssh, mssh) are not affected. Measured on sudo 1.9.16 and 1.8.23. Why not fix: telling "would ask" from "would not" takes running sudo without `-n`: on a terminal that is 0.45's hang (a stopped sudo, and a password typed into it shown in clear), and with no terminal a failed login that pam_faillock counts. The re-review after the second fix round checked for a design that removes this (a probe at the start, asking in the background, a retry in a session of its own) and found none. Workarounds: NOPASSWD for btrfs, or `Defaults noninteractive_auth` on sudo 1.9.10 or later (EL7's 1.8.23 and EL8's 1.9.5 lack it; measured 2026-11-25 by multiCMD 1.71's build on sudo 1.9.16: it makes `sudo -n` sign in with no question, but then pam_faillock counts each refusal of a password sudo as a failed login, so it is no workaround where faillock is set; and sudo 1.9.9 (Ubuntu 22.04) runs PAM for `-n` by default: there a no-question sudo passes `-n`, and each refusal of a password sudo is counted, measured by multiCMD 1.71's final review). Revisit when someone hits it. Options: **(a) known limitation, release 0.46 as built (recommended): every password sudo stops hanging on a terminal, and these setups fail at once where they worked**; (c) release 0.46 with plain `sudo` again but keep the new ask at the start when statbtrfs holds the terminal: nothing is worse than 0.45, but the hang stays wherever no sign-in is remembered (a password typed into the stopped sudo shows in clear, a background run stays stuck), which is itself a known limitation to approve, and it needs one more code round. The rest of 0.46 (the device-stats fix, the docs, the embed) ships either way. What waits on it: 0.46's release. The same trade is multiCMD 1.71's question (its progress file, 2026-11-25: on a terminal its `use_sudo` commands run as `sudo -n`); one answer should fit both. Your words it touches: the release gate (2026-11-09), "releasing a new version gate is only if it does not make an existing issue worse": with (a) these setups get worse while the hang every password sudo hits gets better; with (c) nothing gets worse and the hang stays.
