## Questions waiting for the user
- **Q1 (0.46): a sudo that signs in with no question, on a terminal, after sudo's remembered sign-in has run out: a known limitation?** What the operator sees: with statbtrfs run as a user (not root) through the per-command sudo fallback, on a terminal, where sudo authenticates with no question and no NOPASSWD rule (an ssh agent through pam_ssh_agent_auth, Kerberos), and sudo remembers nothing at that moment (`timestamp_timeout=0`, or `-i` longer than sudo's timeout, 5 minutes by default): the status read says "Could not fetch complete info ..." and the run exits 2, where 0.45 worked. Why not fix: 0.45 ran those commands with plain `sudo`, which hangs, stopped and silent until a Ctrl-C, for every sudo that asks a password in the same state (the bug 0.46 fixes); 0.46 runs them with `sudo -n`, which refuses before it tries any sign-in, and telling "would ask" from "would not" takes running sudo without `-n`, which is the hang. Without a terminal, and for the scrub start, 0.46 keeps 0.45's plain `sudo`, so those cases still work. On sudo 1.9.10 and later, `Defaults noninteractive_auth` lets `sudo -n` try a no-question sign-in (measured on 1.9.16); EL7's 1.8.23 and EL8's 1.9.5 lack it. Revisit when an operator hits it. Options: **(a) known limitation, release 0.46 with it (recommended): every password sudo stops hanging, and one rare setup fails at once where it worked**; (b) build a retry before 0.46 ships: a command `sudo -n` refuses for a password is run once more with plain `sudo` in a session of its own, where sudo has no terminal to ask on (so it cannot hang) and a no-question sign-in still works (a second path through multiCMD for a rare setup; the re-review is sizing it). What waits on it: 0.46's release.
