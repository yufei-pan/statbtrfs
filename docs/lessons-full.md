entries go last, in the same commit as the change:

## 2026-11-07 statbtrfs 0.41: a check that could not tell, or did not finish, is not OK
- Changed: exit code 2 (the check failed) now also stands for a scrub status that could not be read (`unknown`) and a last scrub that did not complete (`aborted`, `interrupted`), where 0.40 exited 0 for both; a scrub that found errors still exits 1. `-s` ends "Scrubs ended; N could not be started, M did not complete or could not be read." where it said "Scrubs finished; N could not be started." A plain run reads again while a reading is `unknown` or `interrupted`, and `-w`'s first poll while one is `interrupted` (`unknown` there takes the 10 s hold); 3 times, 0.5 s apart.
- Why we had to change: 0.40 read "no record" and "the scrub did not end well" as healthy, so a cron monitor on the exit code stayed green after a cancelled or killed scrub, or when btrfs gave no reply. Making those exit 2 first made a plain run exit 2 whenever it collided with another status reader (`btrfs scrub status` takes the status file with `flock(LOCK_EX|LOCK_NB)`; the loser gets no reply): 12 of 300 and 11 of 300 pairs of runs started together on EL7 (btrfs-progs 4.9.1), up to 7% during a background scrub. A finishing scrub also reads `interrupted` for about a millisecond.
- Original design was wrong because: 0.40 had two answers (healthy, problems) for a check with three: it could not tell whether it was healthy. The first fix of that treated one transient read as the final answer, though both transients last about a millisecond and the next read is clean.
- Lesson: a monitor's exit code keeps three answers (fine, not fine, could not tell), and "could not tell" is never "fine". Where the tool read from can fail for a moment (a lock held by another reader, the end of a job), read again a few times with a stated bound before reporting it; the bound caps what a real failure costs (here 1.5 s per run).

## 2026-11-07 statbtrfs 0.43: a filter skips the work, never the check
- Changed: `-d N` still skips the scrub of a filesystem scrubbed within N days, but no longer its check: a skipped filesystem with device errors, scrub errors, a forced read-only state or an unreadable status is shown (row and note) and counts in the exit code, in plain, `-s` and `-w`. A healthy skipped one stays out of the table. So `statbtrfs -s -d 7` and plain `-d 7` exit 1 (or 2) where 0.42 said "nothing to do" and exited 0. Also: a mount that reads read-write on a read-only filesystem is reported as forced only when `BTRFS_IOC_START_SYNC` on it fails with EROFS; success means a deliberate remount (not reported); any other errno means could not tell (exit 2).
- Why we had to change: a weekly `statbtrfs -s -d 7` on a filesystem scrubbed 3 days ago that was then forced read-only (or had device errors) printed "nothing to do" and exited 0, so the monitor stayed green. And the mountinfo signature of a forced filesystem is the same as that of `mount -o remount,ro` on one of several mounts of a filesystem: 0.43's first version reported the remount as an error that never happened.
- Original design was wrong because: `-d` was applied before the check, so what it skipped it also stopped looking at; and one observable (rw mount, ro superblock) was taken to have one cause.
- Lesson: an option that leaves things out must leave out only what is healthy; the skipped part is still checked. When a signal has two causes, ask the system which (here one ioctl, decided by its errno, never by text) before reporting it, and say "could not tell" when it can't answer.

## 2026-11-14 statbtrfs 0.45: a copy you carry is no requirement
- Changed: statbtrfs's package metadata requires no multiCMD (`install_requires` drops `multiCMD>=1.56`, and requirements.txt, which held only `multiCMD`, is gone). statbtrfs runs the multiCMD it embeds (1.67 in 0.45) wherever the installed one is older than that copy, missing, or does not import, and an installed one at least as new, as before.
- Why we had to change: the floor (1.56) was below the copy statbtrfs uses (1.61 in 0.44), so the requirement guaranteed nothing statbtrfs relied on; it only made pip install or upgrade a multiCMD that statbtrfs then passed over. And pip 9.0.3 (stock on EL7 and EL8) upgrades every requirement under `-U`, which stopped the install: with multiCMD 1.55 or 1.57 installed, `pip install -U statbtrfs==0.44` exited 2 with `configparser.DuplicateOptionError` (those versions' `mcmd`, `multicmd` and `multiCMD` entry points, which pip 9 reads as one name). Without the requirement, pip 9.0.3 upgrades 0.44 to 0.45 there (exit 0, multiCMD left as it was, statbtrfs running its embedded 1.67), and with multiCMD 1.67 installed statbtrfs imports that one (the CI's python:3.6 image, 2026-11-14). hpcp dropped its requirement for the same reason in 9.89; the user chose "Drop it, as hpcp did (Recommended)".
- Original design was wrong because: the requirement dates from when statbtrfs needed an installed multiCMD; once statbtrfs carried its own copy and chose between the two by version at import, it stated no need, and a requirement that states no need still hands the installer's own failures to every install.
- Lesson: declare as a requirement only what the program needs from outside it. A library it carries a copy of and picks by version at import is not one.

## 2026-11-14 statbtrfs 0.45: say what a command did from its answer, not from having asked
- Changed: `cancel_scrub()` returns None once `btrfs scrub cancel` exited 0, else what it said (its last line, or its exit code), through a private helper that returns (exit code, reply); `execute_command()` is unchanged. The Ctrl-C prompt of -s, answered y, prints "Cancelled scrub on X: it keeps its progress, continue it with ..." only for a cancel that worked, and "Could not cancel the scrub on X: <what btrfs said>. See where it stands with `btrfs scrub status X`." for one that failed.
- Why we had to change: 0.44 printed "Cancelled scrub" for every scrub, whatever btrfs answered. A scrub that finished while the prompt waited makes btrfs-progs' `cmd_scrub_cancel` fail with "not running" (ENOTCONN), where the resume advice is wrong; behind the per-command sudo fallback a cancel sudoers does not allow is refused and the scrub keeps running while statbtrfs said it was cancelled. Found by the 0.44 final review and deferred to 0.45.
- Original design was wrong because: it took asking for the cancel as the cancel; the command's exit code, the one thing that tells, was dropped with its output.
- Lesson: a report of an action reads the action's own answer, and shows the action's words when it failed; an action asked for after a wait can find its target gone, and one run through a gatekeeper can be refused.

## 2026-11-23 statbtrfs 0.46: a command no one can answer must not ask
- Changed: behind the per-command sudo fallback, the commands multiCMD runs (the discovery, the polls, the `-d` filter's status reads, the scrub cancel) go through `sudo -n` while statbtrfs has a controlling terminal (`/dev/tty` opens; stdin being a terminal is not the test), where they ran through plain `sudo`. One private helper, `_as_root()`, decides. A command sudo wants a password for then fails at once with "sudo: a password is required" (exit 1). The scrub start (a session of its own, no terminal) and every command of a run with no terminal at all keep plain `sudo`. The password asked for at the start (`sudo -l` in acquire_root) is asked wherever statbtrfs holds the terminal (`_in_foreground()`: the terminal's foreground process group is its own) or stdin is a terminal, where it was asked only when stdin was one.
- Why we had to change: multiCMD starts each command in a process group of its own, which is not the terminal's foreground. sudo there, with no remembered password for the command, went to ask: on a pty, sudo 1.8.23 (CentOS 7), 1.9.5 (Rocky 8) and 1.9.16 (Debian 13), with Python 3.6, 3.11 and 3.14, stopped on its terminal access (state T), some versions after printing "[sudo] password for <user>:", and statbtrfs waited for it until a Ctrl-C; a password typed meanwhile went to no reader and stayed on the screen in clear. That happened with sudo set to ask every time (timestamp_timeout=0, at the first poll), for any run whose stdin was not the terminal (`sudo -n -l` leaves no remembered password), and for a Ctrl-C cancel answered after the remembered password ran out, after which a second Ctrl-C left the scrub running with no word about it. Found by the 0.45 second opinion from reading, measured in 0.46.
- Original design was wrong because: it took sudo for a command that runs, and its prompt for one that reaches the person; the password asked for at the start (`sudo -l`, in the foreground) only usually covers the later commands. The first fix, `-n` on every sudo statbtrfs starts, was too wide: `sudo -n` refuses before it tries any authentication, so it also refused a sudo that answers with no question and no NOPASSWD (a PAM ssh agent or Kerberos, an askpass helper with DISPLAY), which 0.45 ran, in the two places where no hang was possible (no terminal; the scrub start's session of its own). The final review measured it, with Rocky 8's own pam_ssh_agent_auth. Asking at the start only when stdin was a terminal took sudo for a program that reads stdin: it reads its password from the terminal. A run with stdin off the terminal (`statbtrfs </dev/null`, a pipe, nohup) got `sudo -n -l`, which refuses before PAM, so even a user whose sudo may run everything fell back to the per-command sudo with nothing remembered, and every `sudo -n` there was refused (0.45 exit 0, the 0.46 build before this fix exit 2; measured on sudo 1.8.23 and 1.9.16). Keeping plain `sudo` where `-n` cannot help (no terminal, the scrub start) brings back 0.45's failed-login count for a password sudo with no terminal (pam_faillock), deferred to 0.47; measured in the re-review.
- Lesson: a command started in a process group of its own, in the terminal's session, runs in its non-interactive form, so its question becomes a failure in its own words, and whatever it needs from the person is asked in the foreground first (for the status and cancel commands, not for a scrub start), on the terminal whether or not stdin is one, since sudo reads its password from the terminal. A job-control stop is a hang its parent never sees. The non-interactive form also skips every way of answering that needs no person (`sudo -n` does not try PAM or an askpass helper). With no terminal, or in a session of its own, the plain form cannot stop at a prompt either (it fails, or asks an askpass helper if one is set), but it is no free choice: it runs PAM, which counts its failure to ask as a failed login (pam_faillock locks accounts for it). There, choose by who must keep working, and say what the other loses.
